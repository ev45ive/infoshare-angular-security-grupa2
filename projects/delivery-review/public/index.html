Jeden mały przepływ: wybór dokumentu, decyzja API, tekst podglądu i artefakt klienta. Każdy panel prowadzi przez obserwację, wskazany kod i zakres dowodu.

Lab prowadzony · 1/4

L3.1 — Od przepływu do testu

Cel: powiązać wymaganie „Anna z organizacji A czyta dokument A” z kontrolą i dowodem. API, a nie ukryty przycisk, egzekwuje granicę tenantów.

  1. Przepływ. Anna wybiera doc_42; klient wysyła ID do API; API sprawdza tenant; klient pokazuje opis jako tekst.
  2. Kontrola i właściciel. W tej fixture API mapuje demonstracyjnego aktora na tenant i sprawdza zasób. Aktor jest symulowany nagłówkiem X-Demo-Actor; rzeczywiste API powinno ustalać tożsamość ze zweryfikowanej sesji lub tokenu. Właściciel kontroli: zespół API. Frontend odpowiada za walidację wiadomości i bezpieczny sink.
  3. Test pozytywny. Wybierz własny dokument. Wynik zawiera dane dokumentu A.
  4. Test negatywny. Anna żąda dokumentu B. API zwraca 404 bez treści dokumentu; log serwera zapisuje odmowę bez opisu dokumentu.

Kod źródłowy: server.ts — endpoint /api/documents/:id; fixture przepływu: fixtures/preview-after.ts.

Obserwuj wynik poniżej i terminal serwera: decision=allow albo decision=deny. Odpowiedź 404 nie dowodzi sama w sobie, że żadna operacja uboczna nie zaszła; tutaj endpoint jest tylko odczytem.

Granica i ryzyko resztkowe: STRIDE

Podszycie pod aktora, naruszenie integralności wiadomości i ujawnienie dokumentu prowadzą do różnych kontroli. Symulowany nagłówek aktora zastępuje rzeczywiste uwierzytelnienie; granica zaufania przesuwa się między kontrolowanym widgetem, portalem i API. Autoryzacja obiektu nie naprawia błędnego uwierzytelniania ani nie usuwa już ujawnionych danych.

Lab prowadzony · 2/4

L3.2 — Review zmiany podglądu

Przejdź od źródła do sinka. Pokazany diff jest małym fixture kodu TypeScript, a przyciski poniżej dowodzą osobno serwerowej decyzji dostępu.

  1. Wejście: event.data.id pochodzi z wiadomości widgetu; sprawdź nadawcę przez origin i source oraz waliduj schemat i format ID.
  2. Decyzja: koduje się segment URL, ale API nadal autoryzuje obiekt po tenantcie. Kodowanie ID nie jest autoryzacją.
  3. Użycie: zwykły opis trafia do textContent, nie innerHTML. Uruchom oba żądania poniżej i porównaj dane oraz log.
  4. Zmiana: w server.ts zmień warunek permitted, uruchom serwer ponownie i powtórz odmowę. Następnie przywróć warunek. Statyczny diff i lokalna odpowiedź nie dowodzą działania produkcyjnego widgetu ani CDN.

Przed review

fixtures/preview-before.ts

window.addEventListener('message', async event => {
  const response = await fetch(`/api/documents/${event.data?.id}`);
  const document = await response.json();
  preview.innerHTML = document.description;
});

Po review

fixtures/preview-after.ts

if (event.origin !== trustedOrigin) return;
if (event.source !== trustedFrame) return;
if (!isDocumentSelected(event.data)) return;
const response = await fetch(`/api/documents/${encodeURIComponent(id)}`);
if (!response.ok) return;
preview.textContent = document.description;

W fixture po zmianie sprawdź też przypadek negatywny. Sama poprawa sinka nie naprawia IDOR; sama autoryzacja API nie zabezpiecza kontekstu HTML.

Wiadomość z widgetu i identyfikator obiektu

Porównaj dwie ramki tego samego originu: tylko pierwsza jest wskazaną instancją. Wyślij z niej poprawne oraz błędne dane, a następnie wyślij poprawne dane z drugiej ramki. Odbiorca sprawdza origin, source i format, zanim wyśle żądanie do API.

Oczekiwanie na wiadomość.

Porównaj niedostateczną i chronioną kontrolę obiektu dla tego samego ID.

Kontekst renderowania i cel URL

Ten sam kontrolowany tekst można wstawić jako tekst lub jako HTML. Porównaj wynik i DOM; CSP również wpływa na możliwość wykonania handlerów. URL parsujemy i porównujemy origin przed użyciem, a nie wyszukujemy fragmentu w ciągu.

L3.3 — Granice CI i zależności

Fixture przedstawia workflow pull requestu i przypiętą zależność. Lokalna demonstracja odczytuje pliki i raportuje ich jawne właściwości; nie wykonuje YAML, instalacji ani pipeline’u.

  1. Otwórz fixtures/dependencies.lock.json: wersja i pole integralności pomagają odtworzyć wybór paczki, ale nie dowodzą, że paczka lub rejestr są bezpieczne.
  2. Otwórz fixtures/ci-workflow.yml: PR ma contents: read, bez sekretu deployu i bez prawa zapisu.
  3. Uruchom symulację. Sprawdź także lifecycle scripts: fixture wykonuje jako tekst tylko statyczną kontrolę i pokazuje, że npm ci nie deklaruje --ignore-scripts.
  4. Zmień w fixture contents: read na contents: write i ponów inspekcję. Porównaj wynik, a potem przywróć plik. Właściciel CI ocenia również runner, źródło kodu i uprawnienia.
  5. Sprawdź zależność przechodnią i jej deklarowany skrypt instalacyjny w lockfile. W fixtures/ci-boundaries.json porównaj PR i release; zmień klucze cache albo nazwę artefaktu na takie same i uruchom ponownie inspekcję. Cofnij zmianę. Pole provenance jest deklaracją fixture, nie weryfikacją kryptograficzną.

Miejsca review: fixtures/ci-workflow.yml i fixtures/dependencies.lock.json. Bez prawdziwych sekretów, runnera ani CI.

Eksperyment automatyczny

E3.1 — Co zawiera artefakt klienta

Kompilator TypeScript przygotowuje mały klientowy artefakt ze źródła i source mapą. Po wejściu na ekran serwer sprawdza te trzy pliki automatycznie; nie trzeba uruchamiać akcji w UI.

Skanowanie lokalnych fixture…

  1. Źródło: artifact/src/client-config.ts.
  2. Bundle: artifact/browser/client-config.js.
  3. Source map: artifact/browser/client-config.js.map.
  4. Porównaj wynik: wpisana do klienta wartość jest publiczna; mapa ujawnia powiązanie z kodem źródłowym. Wartość jest markerem fikcyjnym, nie sekretem.

Build: npm run build w katalogu projektu. Eksperyment wykrywa tylko marker jawnie zapisany w tych fixture; brak trafienia nie jest skanerem sekretów.

L3.4 — Od konfiguracji do odpowiedzi i reakcji

Konfiguracja serwera ma znaczenie dopiero w odpowiedzi odebranej przez klienta. Sprawdź lokalny HTML, JSON API oraz odmowę; następnie prześledź przygotowany incydent i różnicę między rollbackiem a rotacją.

  1. Sprawdź HTML: odpowiedź zawiera CSP i polityki przeglądarkowe ustawione przez serwer HTML.
  2. Sprawdź API i 404: obserwuj Cache-Control, typ treści i zachowanie odmowy. Test dotyczy wyłącznie tego lokalnego serwera.
  3. W server.ts zmień Referrer-Policy, uruchom serwer ponownie i porównaj faktyczną odpowiedź; następnie przywróć konfigurację.
  4. Przejrzyj przygotowane zdarzenia: alert zależności nie rozstrzyga, czy artefakt wykonał kod ani czy credential został skopiowany.
  5. Przywróć stan symulacji, wykonaj rollback i sprawdź stan fikcyjnego credentiala. Potem wykonaj osobno rotację. Rollback artefaktu sam nie unieważnia skopiowanego credentiala.

Konfiguracja i odpowiedzi: server.ts. Zdarzenia: fixtures/incident-events.json. Właściciele decyzji w symulacji: release control oraz operator credentials.

Wszystkie akcje zmieniają wyłącznie stan pamięci tego procesu. Nie ma prawdziwego deploymentu ani credentials.

Odpowiedź po przejściu przez proxy

Porównaj nagłówki produkcyjnej i staging odpowiedzi, a następnie wariant, w którym kontrolowana atrapa proxy usuwa CSP. Spróbuj również odpowiedzi błędu. Obserwuj nagłówki w Network i log; atrapa modeluje zmianę w jednym procesie, nie jest rzeczywistym CDN.

Alert i log

Porównaj alert dotyczący artefaktu wdrożonego i niewdrożonego. Wynik symulacji nie rozstrzyga, czy podatny kod został wykonany. Log żądania zawiera metodę, ścieżkę i wynik, a nie wartość poświadczenia.
