# G2 L2.4–L2.5 — Sesja w ramce i macierz integracji

Samodzielny zestaw pokazuje, jak kontekst top-level i iframe wpływa na cookie sesyjne oraz jak rozdzielić odpowiedzialność za framing, `postMessage` i CORS. Serwer zapisuje do terminala rzeczywiste żądania API wraz z `Origin`, `Cookie` i `Sec-Fetch-Site`; strona portalu pokazuje bieżący log API.

## Uruchomienie

W katalogu głównym `angular-security-labs` uruchom:

```powershell
npm run lab:integration
```

Otwórz [http://app.localhost:4222/l2-4](http://app.localhost:4222/l2-4). Serwer nasłuchuje na `127.0.0.1` na portach 4222–4226. Wymagana jest przeglądarka obsługująca nazwy `*.localhost`. Proces zatrzymuje `Ctrl+C`.

### HTTPS i warianty cookie

Z katalogu głównego repozytorium przygotuj lokalny certyfikat zgodnie z [instrukcją local-origins](../__experiments/local-origins/README.md), a następnie uruchom serwer z przełącznikami:

```powershell
npm run lab:integration:https
```

Otwórz `https://app-a.localhost:4222/l2-4`. HTTPS używa hostów `app-a.localhost`, `app-b.localhost`, `localhost` i `api.localhost` objętych certyfikatem oraz portów 4222–4226. Serwer tylko odczytuje lokalne pliki PEM i nie instaluje certyfikatu do magazynu zaufania. Dla porównania uruchom osobno `npm run lab:integration:https:lax` lub `npm run lab:integration:https:strict`. `SameSite=None` jest wysyłane wraz z `Secure` wyłącznie w trybie HTTPS. Zachowanie third-party cookies zależy od przeglądarki i jej ustawień.

## L2.4 — sesja i żądanie z ramki

1. Otwórz link **login API top-level** w portalu. Endpoint `http://api.localhost:4224/login` ustawia fikcyjne cookie `g2_session` z `HttpOnly`, `SameSite=Lax` i ścieżką `/`.
2. Potwierdź stan sesji na stronie API i wróć do portalu.
3. W ramce widgetu wybierz **fetch API z credentials**. Porównaj wynik z próbą top-level w Network, Storage/Cookies oraz logiem terminala.
4. W Network rozdziel preflight `OPTIONS` od właściwego żądania `POST`. API dopuszcza portal i widget z `Access-Control-Allow-Credentials`; operacja sprawdza, czy przeglądarka dołączyła cookie.
5. Użyj **fetch API z CORS zablokowanym**. API rejestruje odebrane żądanie, ale nie udostępnia odpowiedzi kodowi widgetu. Błąd JS nie dowodzi, że żądanie nie dotarło do serwera.

Cookie jest celowo fikcyjne i nie uwierzytelnia operacji. Top-level API i widget są na odrębnych lokalnych hostach, więc próba mierzy zachowanie przeglądarki dla cross-site iframe. Domyślny tryb HTTP demonstruje `SameSite=Lax`; wariant HTTPS pozwala porównać także `None; Secure` i `Strict`. Zachowanie zależy od przeglądarki i jej ustawień.

## L2.5 — macierz integracji

| Próba | Decyzja i odpowiedzialna odpowiedź | Gdzie sprawdzić |
| --- | --- | --- |
| Portal ładuje widget partnera | `frame-src` odpowiedzi portalu i `frame-ancestors` odpowiedzi widgetu | Działająca ramka, Network i Console |
| Portal próbuje załadować obcy origin | `frame-ancestors` odpowiedzi obcego widgetu | Zablokowana ramka, Network i Console |
| Obcy origin próbuje osadzić portal | `frame-ancestors 'none'` odpowiedzi portalu | Otwórz `http://other.localhost:4225/other`; sprawdź Console i odpowiedź portalu |
| Widget wysyła wiadomość do portalu | Odbiorca w portalu weryfikuje `event.origin`, `event.source` i typ wiadomości | Status portalu i konsola DevTools |
| Widget odczytuje odpowiedź API | Allowlista CORS, credentials oraz cookie dołączone przez przeglądarkę | Preflight, request, response headers i log serwera |
| Widget wywołuje endpoint bez CORS | API pomija `Access-Control-Allow-Origin` | Fetch error w ramce i wpis żądania w terminalu |
| Portal odczytuje DOM widgetu | Same-origin policy przeglądarki | Przycisk „Spróbuj odczytać DOM ramki” i Console |

CORS kontroluje dostęp skryptu do odpowiedzi cross-origin. Nie decyduje, czy dokument może zostać osadzony, nie daje dostępu do DOM ramki i nie uwierzytelnia ani nie autoryzuje operacji API.

## Dodatkowe warianty

Tryb HTTPS i porównanie `Lax`, `Strict` oraz `None; Secure` opisano wyżej. Widget umożliwia też próbę cookie `Partitioned; Secure; SameSite=None` z API oraz odczyt i żądanie Storage Access API w dokumencie widgetu. Sprawdź zapis i klucz partycji w DevTools; wynik, ewentualna prośba o zgodę i obsługa API zależą od przeglądarki. Dostęp do storage widgetu nie jest automatycznie dostępem do cookie osobnego originu API.

Kontrolowane proxy na porcie 4226 przekazuje żądania do widgetu lub API i może usunąć `frame-ancestors` albo `Access-Control-Allow-Origin`. Na stronie obcego originu porównaj dwie ramki widgetu; w ramce widgetu porównaj odczyt API przez proxy z zachowanym i usuniętym CORS. Obserwuj końcowe nagłówki, Console i log `[PROXY]`.

Allowlista CORS odpowiada dynamicznym `Access-Control-Allow-Origin` i `Vary: Origin`; odrzucone originy nie dostają nagłówka zezwalającego, a preflight otrzymuje odmowę. Osobna sandboxowana ramka wysyła preflight z `Origin: null`; widget pokazuje też odpowiedź HTTP 500, którą skrypt może odczytać, gdy CORS jest dozwolony. Przeglądarka może wysłać żądanie, którego odpowiedź skrypt nie odczyta; status serwera i błąd `fetch` obserwuj oddzielnie.

Wariant wiadomości wysyła niewłaściwy `targetOrigin`, a odbiorca sprawdza `event.origin`, konkretne `event.source` i schemat danych. Te kontrole chronią granicę komunikatu, ale nie stanowią autoryzacji endpointu.
